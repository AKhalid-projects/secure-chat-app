# NFR-010: Operational observability

## 1. Requirement Statement

The Secure Chat Application shall emit diagnostic information primarily through JavaScript console logging for errors, token lifecycle events, and handler failures, without an integrated application performance monitoring or centralized log shipping layer in the analyzed codebase.

## 2. Requirement Type

- Non-Functional Requirement

## 3. NFR Category

- Observability

## 4. Description

`console.log` / `console.error` appear in initialization, push handlers, VoIP handler, and global error hooks. No structured logging, metrics, or crash reporting SDK is evidenced in `App.tsx` or `index.js` beyond the error boundary.

## 5. Rationale

Lightweight diagnostics suit development samples; production systems typically need more.

## 6. Quality Scenario

- **Source**: Production incident.
- **Stimulus**: Intermittent crash in field.
- **Artifact**: Client logs.
- **Environment**: End-user device without dev tools.
- **Response**: Limited visibility unless user reports or remote logging added.
- **Response Measure**: Absence of centralized telemetry in repo.

## 7. Measurable Criteria

- Search for logging patterns vs. absence of Sentry/Datadog/etc. in `package.json` dependencies used in src.

## 8. Applicability

- Entire JS layer.

## 9. Constraints / Policies

- Privacy regulations may restrict what can be logged; not addressed in code.

## 10. Evidence from Repository

- `App.tsx` (logging statements)
- `index.js` (global handlers)
- `package.json` (no observability SDK in active src imports)

## 11. Source Confidence

- **Inferred** — Logging is visible; absence of APM is inferred from lack of integration code.

## 12. Verification Approach

- Static code search; device logcat for Android / Xcode console for iOS during manual tests.

## 13. Risks if Unmet

- Slow mean time to resolution for production defects.
