# NFR-004: Runtime configurability

## 1. Requirement Statement

The Secure Chat Application shall support runtime-adjustable product configuration—including feature toggles, tab layout, and style tokens—via JSON defaults, persisted overrides, and store updates without requiring a full application rebuild for many parameters.

## 2. Requirement Type

- Non-Functional Requirement

## 3. NFR Category

- Configurability

## 4. Description

`config.json` seeds Zustand; AsyncStorage holds `@app_config` and `appCredentials`. QR import updates configuration dynamically. This supports white-label and builder-driven deployments.

## 5. Rationale

Operational flexibility reduces time-to-market for variant demos and thesis experiments.

## 6. Quality Scenario

- **Source**: Product owner changes builder output.
- **Stimulus**: New JSON saved to device.
- **Artifact**: Config store.
- **Environment**: Running app.
- **Response**: Tabs and theme update from selectors.
- **Response Measure**: Visible UI matches new settings after reload or store update.

## 7. Measurable Criteria

- Single source of truth in `useConfigStore`; persistence keys documented in `store.ts` and `qr_screen.tsx`.

## 8. Applicability

- Global UI/navigation; not all CometChat server features are client-toggleable.

## 9. Constraints / Policies

- Invalid stored JSON falls back to defaults (`initializeConfig`).

## 10. Evidence from Repository

- `src/config/store.ts`
- `src/config/config.json`
- `src/components/conversations/screens/qr_screen.tsx`

## 11. Source Confidence

- **Explicit** — Store and persistence implemented.

## 12. Verification Approach

- Change stored config; restart app; observe tab/theme changes.

## 13. Risks if Unmet

- Every change requires developer rebuild, slowing evaluation cycles.
