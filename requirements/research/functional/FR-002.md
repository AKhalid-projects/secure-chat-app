# FR-002: Application credentials lifecycle

The Secure Chat Application shall allow operators to enter CometChat application credentials, persist them locally, re-initialise the SDK with updated values, and route first-time users to credential entry when credentials are incomplete. This requirement is **High** priority and belongs to **authentication** and **bootstrap** domains. It reflects stakeholder needs for configurable tenancy in demonstration and coursework contexts, where application identifiers and keys may change without rebuilding native binaries from scratch.

The requirement captures both **data** and **control-flow** obligations. Credential fields must be validated before persistence; storage uses a documented local key; re-initialisation aligns the SDK with newly saved values; navigation advances toward user selection or login once persistence succeeds. When credentials are missing or incomplete at cold start, the navigation shell routes to the credential screen rather than assuming valid defaults, which supports honest scoping in academic reporting.

Evidence appears in the dedicated credential screen module and in the root shell logic that evaluates whether credentials are complete. **Explicit** confidence applies because persistence, validation messaging, and navigation are directly observable in source. Verification includes walking the credential entry flow, confirming storage contents conceptually, and observing navigation reset behaviour toward login.

This requirement interacts closely with **FR-001** (initialisation parameters) and with **NFR-005**, which documents client-side handling of secrets at a quality level rather than as a production hardening claim.
