# FR-001: CometChat SDK initialisation

The Secure Chat Application shall initialise the CometChat UIKit with a valid application identifier, authentication key, region, and subscription type that includes all users, before presenting authenticated functionality. This requirement is classified as **High** priority within the functional catalogue and falls under **integration** and **bootstrap** concerns. It was validated against the reference implementation following stakeholder emphasis on reliable connection to the communications backend.

From a systems perspective, initialisation establishes the runtime contract between the mobile client and CometChat’s cloud services. Without it, messaging, presence, and call-related application programming interfaces cannot be invoked meaningfully. Workshop discussion treated tenant configuration as a prerequisite for any demonstration of chat or voice features; the requirement therefore anchors the remainder of the functional set.

In implementation, the application resolves credentials from asynchronous local storage or from compiled defaults, invokes initialisation with an all-users subscription type, and leaves a blocking load state once the attempt completes. A persisted user session, when present, influences subsequent routing. Repository evidence is concentrated in the root application module, where the initialisation effect is declared. Source confidence for this requirement is **explicit**, because the initialisation sequence appears directly in application code rather than being implied solely through dependencies.

Verification proceeds through inspection of the initialisation path and through execution on a device or simulator: successful launch should complete initialisation before interactive credential or login surfaces appear, subject to credential validity rules treated under related requirements. **FR-002** addresses credential capture and persistence; **NFR-011** addresses dependence on third-party service integration at a quality level.
