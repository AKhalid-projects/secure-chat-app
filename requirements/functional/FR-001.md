# FR-001: CometChat SDK initialization

## 1. Requirement Statement

The Secure Chat Application shall initialize the CometChat UIKit with a valid application identifier, authentication key, region, and subscription type that includes all users, before presenting authenticated functionality.

## 2. Requirement Type

- Functional Requirement

## 3. Module / Domain

- Integration
- Bootstrap

## 4. Description

On launch, the application resolves CometChat tenant credentials (from local storage or compiled defaults), invokes `CometChatUIKit.init` with the resolved `appId`, `authKey`, `region`, and `SUBSCRIPTION_TYPE_ALL_USERS`, and transitions from a loading state to the main navigation shell when initialization completes. This establishes the runtime binding to the CometChat backend used for messaging and calls.

## 5. Rationale

Without successful SDK initialization, no CometChat API (messages, calls, presence) can operate. This is the foundational step for the entire Secure Chat Application.

## 6. Inputs

- Optional JSON object in AsyncStorage key `appCredentials` (`appId`, `authKey`, `region`).
- Fallback values from `AppConstants` when storage is empty.
- CometChat SDK and UIKit packages loaded in the application bundle.

## 7. Processing / Behavior

1. Read stored credentials or use `AppConstants`.
2. Call `CometChatUIKit.init` with the resolved parameters and `subscriptionType` `SUBSCRIPTION_TYPE_ALL_USERS`.
3. Set application state to reflect initialization completion (e.g., end splash/blank state).
4. If a persisted CometChat user session exists (`CometChatUIKit.loggedInUser`), mark the user as logged in for routing.

## 8. Outputs

- Initialized CometChat UIKit runtime.
- `isInitializing` becomes false; UI proceeds to credential/login or main flow.
- `isLoggedIn` may be true if a session already exists.

## 9. Preconditions

- Valid network eventual availability (errors may be logged; exact behavior depends on SDK).
- Credentials eventually resolve to non-empty `appId`, `authKey`, and `region` for full credential validity checks elsewhere.

## 10. Postconditions

- CometChat UIKit is initialized for the current process or initialization failed with logged error.

## 11. Error Handling / Exceptions

- Initialization errors are caught and logged; initialization still completes from a UI perspective (`finally` sets initializing false).

## 12. Business Rules / Constraints

- Subscription type is fixed to **all users** in the implementation as cast to UIKit settings.

## 13. Dependencies

- `@cometchat/chat-uikit-react-native`, `@cometchat/chat-sdk-react-native`.
- `@react-native-async-storage/async-storage` for stored credentials.
- `AppConstants` defaults.

## 14. Evidence from Repository

- `App.tsx` (init effect, `CometChatUIKit.init`).

## 15. Source Confidence

- **Explicit** — Initialization is directly implemented in application code.

## 16. Acceptance Criteria

- Given the device has valid credentials in storage or defaults,
- When the application launches,
- Then `CometChatUIKit.init` is invoked with `appId`, `authKey`, `region`, and `SUBSCRIPTION_TYPE_ALL_USERS` before the main UI is shown after the initial load.

- Given no logged-in user exists after init,
- When initialization completes successfully,
- Then the app may proceed to credential or login screens per routing rules.

- Given initialization throws,
- When the error is handled,
- Then the app still leaves the blocking splash state and logs the error (see implementation).
