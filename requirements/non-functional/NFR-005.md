# NFR-005: Client credential and token handling

## 1. Requirement Statement

The Secure Chat Application shall store CometChat application credentials and rely on device push tokens in client-side storage and memory subject to platform APIs, and shall expose push provider identifiers for registration with CometChat.

## 2. Requirement Type

- Non-Functional Requirement

## 3. NFR Category

- Security

## 4. Description

`AsyncStorage` persists `appCredentials` (app id, auth key, region). `AppConstants.tsx` embeds default credentials and `fcmProviderId` / `apnsProviderId`. Push tokens are handled in memory and passed to CometChat registration helpers. This pattern favors demo velocity over hardened secret management.

## 5. Rationale

Without a backend token exchange, the sample stores tenant secrets on-device—a known tradeoff for prototypes.

## 6. Quality Scenario

- **Source**: Attacker with device access.
- **Stimulus**: Extraction of storage or binary constants.
- **Artifact**: Client app data.
- **Environment**: Lost/stolen device or rooted phone.
- **Response**: Potential exposure of CometChat credentials.
- **Response Measure**: Risk review flags need for Auth Key rotation and server-mediated auth for production.

## 7. Measurable Criteria

- Presence of AsyncStorage keys and constant fields (review).

## 8. Applicability

- Bootstrap, push registration, credential screens.

## 9. Constraints / Policies

- Production systems should replace embedded auth keys with secure issuance; **not enforced in code**.

## 13. Risks if Unmet

- Credential leakage, unauthorized CometChat API use, or push impersonation if devices compromised.
